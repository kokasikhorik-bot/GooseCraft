# Архитектура GooseCraft

## Созданное дерево

```text
GooseCraft/
├── src/
│   ├── client.goose              # CLI и точка входа нативного клиента
│   └── core/
│       ├── core.goose            # входной модуль пакета core
│       ├── world.goose           # чанк 16³, проверка координат, тестовый слой
│       └── simulation.goose      # состояние и один детерминированный шаг
├── launcher/goosecraft.cmd       # первый отдельный лаунчер для Windows
├── tests/
│   ├── headless.goose            # тестируется настоящее Goose-ядро
│   └── fixtures/type_error.goose # намеренная ошибка: проверка компилятора
├── tools/
│   ├── bootstrap.py             # получение и сборка закреплённого Goose
│   ├── project.py               # build / test / package
│   └── requirements.txt         # закреплённый CMake
├── .devcontainer/              # закреплённая Linux-база и devcontainer
├── .dockerignore
├── .github/workflows/build.yml  # Linux + Windows x64, headless-проверки
├── toolchain.lock.json          # ревизии и параметры сборки
├── docs/                        # решения, аудит и реальные результаты
├── licenses/                    # неизменённые лицензии upstream
├── THIRD_PARTY_NOTICES.md
├── AGENTS.md
└── LICENSE
```

`.cache/`, `.venv/`, `build/`, `dist/` создаются в облаке и не отслеживаются Git.
В `.cache/upstream/horizon` находится только исследовательская копия; для сборки
GooseCraft она не нужна и сценарием bootstrap не скачивается.

## Границы компонентов

`launcher -> процесс goosecraft-client -> core (world, simulation)`.
Лаунчер знает только расположение исполняемого файла и его CLI. Он не содержит
игровых правил. Клиент и ядро написаны на Goose. Сборочные сценарии на Python
не моделируют мир: они запускают настоящий Goose-код и проверяют результаты.

Чанк сейчас — фиксированный массив `u8[4096]`, индекс `x + 16*(z + 16*y)`.
Идентификаторы 0 и 1 обозначают пустоту и тестовый твёрдый блок, а не реестр
Minecraft. Фикстура не является реализацией генератора Minecraft.
`tick` пока только увеличивает счётчик; частота реального времени не заявляется.

В последующих этапах появятся `src/render`, `src/platform`, `src/assets`,
`src/protocol`, но пустых заглушек с выдуманным API сейчас нет. Рендерер будет
читать состояние ядра, а ядро не должно импортировать `gfx`. Поэтому headless
сборка останется независимой от окна, видеодрайвера и Minecraft-ресурсов.

Для изменяемого мира сначала нужны фиксированные/ограниченные массивы чанков,
явные владельцы пулов и тесты их времени жизни. Нельзя механически переносить
Rust `Arc`, изменяемый граф ссылок или обычную кучу в модель Goose.
Нативные библиотеки допустимы как системная/графическая инфраструктура;
генерация мира, симуляция и игровая логика остаются в Goose.

## Этапы и критерии готовности

1. **Инструментарий и headless-основа (текущий).** Собрать закреплённый Goose,
   проверить нативный бинарник, ядро и ошибочные входы; подготовить Windows CI.
   Windows-проверка останется открытой до настоящего запуска Actions.
2. **Графическая возможность.** Закрепить goose_gfx и его транзитивные зависимости;
   проверить сборку и показ окна/кадра. В облаке отдельно проверить программный
   Vulkan при доступности; Windows GUI не объявлять проверенным по headless-тесту.
3. **Играбельный собственный voxel-прототип.** Камера, движение, коллизии,
   меш чанка, установка/удаление блоков, оригинальные процедурные цвета.
   После этого пользователь начинает локальные проверки Windows 10 x64.
4. **Лаунчер с UI и доставка.** Версии, настройки, логи, проверенные артефакты;
   никаких обязательных локальных инструментов разработчика.
5. **Совместимость Java Edition.** Сначала выбрать конкретную версию игры и
   измеримые сценарии. Затем форматы/протокол/правила с отдельными тестами.
   Совместимость и parity не выводятся из успеха сборки или наличия кубов.
