# Направление GooseCraft

Цель: самостоятельный эффективный нативный клиент на Goose, затем
подключение к серверам Minecraft Java Edition. Все игровые правила,
представление мира, декодирование протокола и применение серверных обновлений
должны оставаться на Goose. Python обслуживает сборку и проверки.

## Ближайшие результаты и оценка сроков

Нативный одиночный voxel-прототип с ходьбой, правками и сохранениями уже есть;
Windows ZIP запускается без установки инструментов разработки. Окно на
пользовательской Windows 10 ещё требует реальной проверки.

Следующая функциональная цель — более удобная одиночная альфа: более высокая
модель мира, оригинальные текстуры/освещение, выбор блоков/инвентарь и удобная
доставка. Не нужно доводить каждую микрооптимизацию маленькой сцены до идеала:
новые оптимизации берём по измеренным задержкам, сохраняя время на игровые функции.
Сетевая цель после подготовки модели данных — конкретная версия Java Edition,
сначала status, затем вход/чанки/движение на контролируемом тестовом сервере.

При регулярных активных итерациях ориентир для удобной одиночной альфы —
несколько недель, для первого ограниченного серверного входа — несколько
месяцев. Полноценная замена Minecraft с широкой совместимостью — проект
на год и больше для небольшой команды. Это оценка масштаба, не календарное
обещание: объём совместимости, поведение Goose/toolchain и Windows-драйверов
ещё не известны полностью. Быстрый ping сервера не считается готовым клиентом,
а FPS-преимущество требует одинакового контента и физического GPU.

## Измеримая эффективность

Первый игровой цикл уже позволяет проверить движение и редактирование.
Теперь снимаем лишнюю работу: компактные меши, повторное использование GPU
буферов и обновление HUD только при изменениях. [Первый отчёт](optimization-1.md)
сохраняет и выигрыш, и регрессии; тесты поверхности и reference-рендерер
не дают выдать исчезнувшую геометрию за оптимизацию.

В [0.5](multichunk-results.md) реализованы девять чанков с явными владельцами,
запросами к соседям, отсечением внутренних граней на стыках и dirty-флагами.
Правка внутри перестраивает один чанк, на границе — также соседей; после
начальной подготовки действует бюджет два чанка на кадр и frustum culling.
Потоки добавляются после профилирования и проверки реального Goose thread API.

Сохранение/загрузка [своего формата](world-format.md) также реализованы.
В [0.6](terrain-results.md) появился детерминированный рельеф по seed,
с проверкой одинаковых GCW-байтов по фиксированным SHA-256 векторам.
Обзор рельефа выявил одиночные просветы при GPU-растеризации greedy-меша.
В [0.6.1](stitch-results.md) согласованы рёбра, исчезли оба наблюдавшихся
просвета; измерены увеличение геометрии и замедление CPU-построения.
На 16 обзорах (четыре seed × четыре стороны) замкнутых clear-пикселей нет,
но точное равенство всех пикселей с reference не заявляется.
В [0.7](profiling-results.md) добавлены p50/p95/p99 CPU loop wall time,
стадии и raw samples, remesh/draw/upload, известные ёмкости/создания буферов.
Отдельный tail flush показывает отложенную GPU-работу offscreen; GPU timestamps
и полная RAM/VRAM пока не измерены. Дальше — более крупный мир, потоковая
загрузка и системное профилирование памяти/кадров на физической видеокарте.
В [0.8](large-world-results.md) мир расширен до 81 чанка/144×144, владелец
блоков получил growable tail, GCW v2 сохраняет большие размеры. Это ещё
полностью резидентный конечный мир: все меши готовятся до первого кадра.
Потоковая подгрузка/выгрузка, seed/координаты в paged storage и более высокая
вертикаль потребуют следующего этапа и явного версионного перехода.
В [0.9](residency-results.md) реализован первый отдельный слой подгрузки:
ограниченная GPU-резидентность 25 мешей с вытеснением и очередью по близости.
Файлы и все 81 CPU-чанк остаются прежними. Следующий шаг — bounded CPU-пул,
страницы хранения с координатами/seed и явный переход с полных GCW v1/v2.
В [0.10](paging-results.md) этот шаг реализован отдельным backend: фиксированный
CPU-пул 49, seed и immutable страницы чанков, атомарный индекс, безопасный
перенос в новый каталог и экспорт обратно в GCW. Вся логика — Goose;
тонкий C-слой делает ограниченное чтение и системную блокировку файла.
Мир пока конечный (81 чанк), I/O синхронный. Следующие задачи — устранить
задержки подгрузки и подготовить индекс/высоту для более крупных миров;
простого снятия границ текущей модели недостаточно для бесконечного мира.
В [0.11](prefetch-results.md) подготовка вынесена в один native Goose worker,
с ограниченными typed queues, versioned results и кешем 8 страниц. Путь
fallback/commit остаётся синхронным; пауза после R ещё не устранена.
Дальше нужно сократить работу именно на таких переходах и измерить кадры
на физическом GPU; число фоновых задач само по себе не доказывает рост FPS.
В [0.11.1](fallback-results.md) убрано до восьми повторных чтений на переход:
успешный синхронный preflight остаётся в свободных слотах того же кеша.
На файловом replay 30 main reads вместо 38; при искусственных 2 мс кадр R
всё ещё около 64,5 мс. Следующий шаг — отдельная ограниченная по кадрам
подготовка большого перехода с явным ожиданием готовых данных: нельзя
продолжать физику или построение мешей по отсутствующим CPU-страницам.
Начальная загрузка, commit и неподготовленные страницы всё ещё синхронные.
В [0.12](transfer-results.md) добавлен opt-in deferred R: preflight/admission
используют прежний worker и staging 8, основной поток принимает максимум два
чанка за кадр. Окно продолжает рисоваться, симуляция ждёт готовой области.
Это не общий async paging: walking fallback и save/commit остаются прежними;
полное ожидание на быстрых файлах может увеличиться.
В [0.13](inventory-results.md) выполнен первый функциональный шаг: hotbar
с девятью слотами и творческий инвентарь двух материалов. Перенос/замена/очистка,
клавиши 1–9, освобождение мыши, безопасное закрытие и focus loss проверены.
Количество предметов, крафт и сохранение раскладки пока отсутствуют. Следующий
приоритет — более высокая модель мира, затем оригинальные текстуры и освещение.
В [0.14](tall-results.md) введён отдельный full-resident Tall backend высотой
64, отрицательные Y, вертикальные dirty/halo/physics и явная миграция GCW v1/v2.
Это ещё не modern Minecraft height и не вертикальный paging: дальше понадобятся
sparse sections/3D storage policy. Следующая видимая функция — оригинальные
текстуры/освещение на этой модели с сохранением корректного ключа greedy-merge.
У нынешнего greedy-меша два непрозрачных материала и постоянный
цвет грани. При добавлении света, AO, прозрачности и текстур ключ объединения
обязан учитывать эти данные; соединять несовместимые грани нельзя.
В [0.15](occlusion-results.md) выполнен первый световой этап: optional vertex AO
на прежних материалах, точный ключ/консервативное объединение и диагональные
dirty-зависимости. Это ещё не распространяемый skylight/block light. Следующий
видимый этап — оригинальные повторяемые текстуры с корректными UV на greedy
прямоугольниках; далее более удобный launcher/settings и данные освещения.

Сравнение с Minecraft потребует одинакового содержимого мира, дальности,
видеонастроек, оборудования и записанного сценария. Маленький benchmark
мешеобразования не доказывает более высокий FPS или меньший общий расход RAM.

## Доставка

Windows x64 продолжает собираться GitHub Actions. Локальные инструменты
разработки пользователю не нужны. После проверки первого прототипа — лаунчер
с интерфейсом, версиями, логами и проверкой скачанных артефактов. Окно на
Windows 10 и её драйвере проверяется отдельно от облачного Linux/Xvfb.

## Совместимость с серверами Java Edition

Сейчас сетевого клиента нет. Перед его реализацией фиксируем конкретную
версию Java Edition и набор проверочных серверов. Совместимость с одной
версией не означает поддержку всех версий, модов и плагинов.

1. **Двоичные кодеки на Goose.** VarInt/VarLong, big-endian числа, UUID,
   UTF-8 строки и ограничения размеров, фрейминг пакетов. Headless-тесты
   дробления/склейки чтений, неверных длин и усечённых данных.
2. **Проверенный транспорт.** В закреплённой stdlib Goose v1 networking
   отсутствует (`docs/stdlib.md` upstream). Понадобится отдельно проверенный
   пакет или декларации C ABI системных TCP API для Windows/Linux.
   Системный ввод/вывод не должен переносить игровые правила из Goose.
3. **Handshake и status/ping.** Сначала реальное получение статуса тестового
   сервера. Успешный ping ещё не является входом игрока.
4. **Вход и состояния протокола.** Login, шифрование/сжатие и configuration
   для выбранной версии; online-mode — через законную учётную запись и
   предусмотренную сервером проверку сессии. Библиотеки криптографии/TLS
   подключаются с сохранением лицензий, собственная криптография не пишется.
5. **Мир от сервера.** Реестры блоков/измерений, chunk sections и palettes,
   освещение, обновления блоков, позиция/телепортации, keep-alive, сущности
   и обязательные подтверждения. Тестовые ID 1/2 не считаются Minecraft IDs.
   Версионный адаптер переводит данные сервера в внутреннее представление.
6. **Игровая проверка.** Законно развёрнутый тестовый сервер, вход, получение
   чанков, движение, изменение блоков и корректное отключение. Сервер остаётся
   источником истины; предсказание клиента проверяется на соответствие
   правилам целевой версии. После этого — расширение списка серверов.

Minecraft jars, извлечённые ресурсы и пользовательские токены в Git не попадают.
Проект не запускает оригинальный Minecraft или Horizon вместо своего клиента.
На текущем этапе никакой доступ к серверам и сетевая совместимость не заявляются.
